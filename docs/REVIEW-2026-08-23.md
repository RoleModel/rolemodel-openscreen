Two parts: the sequence that is actually true today, and the holes to fix.

Everything below came from reading the code and running `lib/verify.mjs`, not
from the docs. The docs are one of the holes.

# Part 1 — The actual steps

## Using it

**Before you start:** macOS, and Homebrew already installed. Nothing else.
Not Xcode, not Node, not Python — `docs/KICKOFF.md` is right about that.

```sh
brew tap rolemodel/tap
brew install rolemodel/tap/rm-video                    # the toolkit + Node
brew install --cask rolemodel/tap/rolemodel-openscreen # the app
rm-setup                                               # the per-user pieces
```

Then **open Openscreen** from Spotlight, the Dock, or `/Applications` — like any
other Mac app.

That last step is the whole answer to "what do I run": nothing. You don't type a
command. `electron/main.ts` calls `openStudio()` immediately after
`createWindow()`, so the Studio comes up as a window with the app. It finds
`rm-studio` on PATH itself, asks the OS for a free port, and spawns it with
`--no-open`.

**Don't launch it from a terminal.** `openscreen` is on PATH, and bare
`openscreen` does reach the GUI — but macOS attributes Screen Recording
permission to whatever process hosts Electron, so launching from a shell grants
it to Terminal.app instead of Openscreen. Your own cask caveats say this. The
recorder then fails in a way that looks like a bug.

`openscreen` on PATH is for the headless verbs — `record`, `export`, `sources`,
`pack`, `captions`, `info`, `open`. `parseCliArgs` routes a subcommand to
`runCli`; reaching the GUI with no subcommand is a fallthrough, not a feature.

### Steps 3 and 4 don't work yet

- **The cask 404s.** `packaging/rolemodel-openscreen.rb` is pinned at
  `version "0.0.0-unreleased"` with zeroed checksums. See hole **H9**.
- **`rm-setup` isn't on PATH.** Nothing installs it. See hole **H1** — this also
  means the one-line installer fails.

So today the honest sequence for a new person is: install the toolkit, clone the
repo, and run the Studio in a browser. Which is the developer path.

## Working on it

```sh
git clone https://github.com/RoleModel/rolemodel-openscreen.git
cd rolemodel-openscreen
npm install
npm run dev          # Studio + live reload, opens localhost:4600
```

`npm run studio` is the same thing without the watcher. **This** is where
`rm-studio` and `:4600` are true — it's how the Studio gets worked *on*, not how
a video gets made.

`npm run forks` fetches the two forks as siblings, with the upstream remote set
up. Only needed to build the app or run the review instance.

```sh
npm run check        # 405 assertions. Currently 2 fail — H5 and H6.
npm run build        # sync-brand -> optics.css -> wallpapers
```

## The one-liner

```sh
curl -fsSL https://raw.githubusercontent.com/RoleModel/rolemodel-openscreen/main/install.sh | sh
```

Does steps 1–4 above. Two problems: the raw URL 404s until `main` is pushed
(**H10**), and it dies at its last step (**H1**).

### H1 — `rm-setup` is on no PATH, so `install.sh` dies at its last step

`bin/rm-setup.mjs` exists. It is in **neither** `package.json`'s `bin` map nor
the formula's `ENTRIES`. Nothing puts it on PATH.

`install.sh:111`:

```sh
if have rm-setup; then
    ...
else
    die "rm-video installed but rm-setup is not on PATH — brew doctor may explain why"
fi
```

So the one-command install runs all the way through tapping, installing the
toolkit and attempting the cask, then **dies** — after the message telling you it
is handing off to the thing that repairs everything Homebrew can't.

**Fix, two lines:**

```jsonc
// package.json, "bin"
"rm-setup": "./bin/rm-setup.mjs",
```

```ruby
# packaging/rm-video.rb
ENTRIES = %w[rm-video rm-studio rm-voice rm-mux rm-library rm-demo rm-share rm-setup].freeze
```

### H2 — `rm-share` is missing from the formula

It's in `package.json`'s `bin` but not in `ENTRIES`, so Homebrew installs six of
the eight commands. `docs/KICKOFF.md:70` promises it in the table. Same one-line
fix as H1 above.

### H3 — nothing asserts the command lists agree

Three lists have to stay in sync and none of them check each other:

- `bin/*.mjs` on disk — 8
- `package.json` `bin` — 7 (no `rm-setup`)
- `packaging/rm-video.rb` `ENTRIES` — 6 (no `rm-setup`, no `rm-share`)

405 assertions and this got through, which is the actual lesson. The formula's
own `test do` block asserts every `ENTRIES` entry got linked — but `ENTRIES` is
the list that's wrong, so it passes.

**Fix:** add a check to `lib/verify.mjs` that reads all three and fails on any
difference. The formula comment already says why this matters — *"`rm-video` was
the only entry point linked, which meant `rm-studio` ... was reachable only by
typing a path into libexec"* — so this is the second time.

### H4 — four docs name the wrong run command

All of these predate fork commit `8b77adb` ("Host the RoleModel Studio as a
window in this app") and describe the world before it:

| file:line | says |
|---|---|
| `README.md:13` | "Then `rm-studio`, and open <http://localhost:4600>." |
| `docs/KICKOFF.md:70` | "`rm-studio` \| **serves the Studio on :4600 — this is the one to run**" |
| `docs/KICKOFF.md:111` | "Open the app, or run `rm-studio` and go to localhost:4600" |
| `install.sh:122` | "Done. Start it with: `rm-studio` # the Studio, on :4600" |
| `packaging/rm-video.rb:65` | "`rm-studio` is the one to open — it serves the Studio on :4600." |

Two things wrong in each: `rm-studio` isn't what a user runs, and `:4600` isn't
the port when the app hosts it — `electron/studio/server.ts` calls `freePort()`.

**Fix:** rewrite each to "open Openscreen", and move `rm-studio` / `:4600` to a
clearly-labelled developer section. `KICKOFF.md:111` is closest to right already
— it just has the order backwards.

Worth an assertion too: `lib/verify.mjs` already reads `install.sh` (line 788),
so it could fail on any doc that pairs `rm-studio` with "run" or ":4600" outside
a dev section. This is the specific failure that cost two wrong answers today.

### H5 — `npm run check` fails: `rm-framed` isn't framed

```
✗ no recipe sets a radius it cannot use — rm-framed: radius 36 on a bottom border
```

`brand/wallpapers.json`, `rm-framed` ("RoleModel · framed board"):

```json
"border": { "width": 19, "color": "#dea7fb", "inset": 0, "radius": 36, "sides": "bottom" }
```

`BORDER_SIDES` is `['bottom', 'all']` and the default is `'bottom'`
(`lib/wallpaper.mjs:31,53`). A bottom rule has no corners, so the radius does
nothing.

This looks like a regression, not a typo: the recipe is *named* framed, and
`README.md` calls it the example of the solid border. When `sides` was added with
`'bottom'` as the default, `rm-framed` silently became a bottom rule and kept a
radius that draws nothing. **The wallpaper called "framed" has no frame.**

**Fix:** `"sides": "all"` on `rm-framed`, then re-render (`npm run wallpapers`)
and look at it. If a bottom rule was actually intended, drop the radius to 0 and
rename it — but I don't think that's what happened.

Also worth noting: it's the only recipe with a non-zero radius, and 15 of 17 have
`width: 0`. The border feature is used by four wallpapers total.

### H6 — `npm run check` fails: a stale assertion, not a bug

```
✗ review reports what is missing
```

`lib/verify.mjs:968` requires the literal string `OPENFRAME_URL` inside the
`/api/review` handler:

```js
check("review reports what is missing", /configured: false/.test(review) && /OPENFRAME_URL/.test(review));
```

The handler was since refactored to read `openFrameSettings()` — environment
*and* a stored file, with the comment *"a GUI launched from Finder has no shell
environment, so the environment alone made this unconfigurable from inside the
app."* That's a real improvement. The env var name is no longer in that function.

The behaviour the assertion means to protect is still there:

```js
return json(res, 200, {
  configured: false,
  missing: [!base && "url", !token && "token"].filter(Boolean),
  source,
});
```

**Fix the assertion, not the code.** Assert on `configured: false` plus a
`missing` array naming url and token — behaviour, not a literal env var. As
written it tests an implementation detail that a legitimate refactor removed.

### H7 — the OpenScreen cross-check silently skips

`verify` ends with `1 skipped (no OpenScreen checkout)`. It needs
`--openscreen /path/to/checkout`, and `npm run forks` puts one at `../openscreen`
— it just doesn't look there.

This is the assertion that reads `ProjectEditorState` and the annotation
interfaces out of the real source and checks every preset field against them. Per
`README.md`, it exists because *a wrong field name doesn't error — OpenScreen
normalises it back to a default and the video silently looks stock.*

So the most expensive check in the suite is the one that quietly doesn't run.

**Fix:** default to `../openscreen` when the flag is absent and the directory is
there. Keep the skip, but make it say "pass `--openscreen` or run `npm run forks`".

### H8 — `bin/dev/openscreen-fork` is stale

Its own header: *"TEMPORARY... All of this goes away when the Studio moves inside
the app — there is no PATH, no probe and no shim when the editor is a window in
the same process."* That shipped in `8b77adb`. Nothing references the file.

**Correction to something I said earlier:** the `openscreen` shim and
`openInOpenScreen()` are **not** dead. `lib/verify.mjs:989` deliberately keeps
them — *"the CLI path survives for a browser"* — because a Studio in a browser
tab has no host to ask. Only `bin/dev/openscreen-fork` is stale, and only its
last paragraph is wrong.

**Fix:** delete it, or rewrite the header to say it's for running the fork from a
checkout when you haven't installed the cask, which is still useful.

### H9 — the cask has no release to point at

`packaging/rolemodel-openscreen.rb`: `version "0.0.0-unreleased"`, both `sha256`
values zeroed. `brew install --cask` 404s.

**Fix (manual, once — not a code change):**

1. Open <https://github.com/RoleModel/openscreen/actions>
2. Click "I understand my workflows, go ahead and enable them"
3. `v1.9.6-rm.1` is already tagged, so the build starts on its own
4. `node packaging/update-cask.mjs rolemodel-openscreen v1.9.6-rm.1`, then
   `npm run sync-tap`

`install.sh` already degrades well here — it warns and leaves a working toolkit
rather than failing the install. That part is right.

Small thing while you're in there: `packaging/update-cask.mjs`'s own usage
comment still says `node scripts/update-cask.mjs`, its pre-restructure path.
`docs/KICKOFF.md:88` repeats it. The argument parsing is fine — name, then a
`v…` tag or `--latest`, with `--check` to verify without writing.

### H10 — the `install.sh` raw URL 404s

`install.sh` is committed but `main` hasn't been pushed, so the URL in
`README.md:10` doesn't resolve. Push and it works.

### H11 — "seven commands"

`docs/KICKOFF.md:70` and `README.md` both say seven. There are eight on disk. The
missing one is `rm-setup` — the same one nothing installs. Fixing H1 and H3
should include correcting the count wherever it's written down.

## What I'd do first

H1, H2 and H3 together — maybe twenty minutes, and they're what stands between a
new person and a working install. H5 is next because it's visible in the output.
H4 is the biggest by volume and the least urgent, but it's the one that made this
repo hard to reason about from the outside, including for me.

H6 and H7 are check-suite hygiene: one assertion is wrong, one doesn't run.

## What I checked and found fine

Not everything needs fixing, and it's worth saying which parts are load-bearing:

- 402 of 405 assertions pass, and they assert real contracts — paused animations,
  no hand-written hexes in the Studio, the vendored Optics copy unedited, pip
  never touching a managed environment, no API key passed as an argument.
- The two forks are genuinely small, and the reasoning for keeping them forks
  rather than vendoring is sound and written down.
- The narration design — per-line synth, measured durations, SRT from what was
  measured — is correct and the rejected alternative is documented.
- `rm-mux`'s two-clocks handling, and the choice to tell you rather than silently
  stretch past `--max-stretch`.
- The shim's reason for existing (Electron helper resolution through a symlink)
  is real and well documented in three places.
